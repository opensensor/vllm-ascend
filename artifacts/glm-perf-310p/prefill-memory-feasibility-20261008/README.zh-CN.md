实现更新：显式启用的源码候选现已实现并通过 CPU 验证，见[实现说明](IMPLEMENTATION.zh-CN.md)。

## 结论

当前压缩器状态以四个 token 为一页，从全局 block-ID 池分配。每个 ID
对应每卡 **7.96875 MiB** 的物理容量，其中包含压缩器不使用的注意力存储。
调度块从 640 增大到 1,280，仅启动准入要求就增加每卡 **1.245117 GiB**。
这还不包括激活、临时工作区和图内存增长。

优先考虑的离线方案是：把八个四-token 压缩池装入一个 **32-token 状态页**。
FP32 原始状态占 32 KiB，仍能放入现有 40 KiB 的填充页；压缩比例保持为四，
MTP1 的保守滑动窗口设为 33 token。1,280 调度块的准入内存可减少每卡
**2.178955 GiB**。此布局尚未接入服务路径，也没有通过硬件验证。

本轮没有启动、恢复、探测服务器或运行 NPU 基准。最近已知的 1,280-token
试验启动失败；此前健康的 640-token 快照只是历史证据。等待中的控制器是否
清理完成尚未确认。

## 精确准入计算

部署包含 12 个主存储槽和 12 个小存储槽，包括 MTP：

- 主页面：640 × 512 × FP16 = 655,360 字节。
- 索引页面：160 × 128 × FP16 = 40,960 字节。
- 全局 ID：12 × 两类页之和 = 8,355,840 字节。
- 四-token 压缩器实际状态：4 × 256 × FP32 = 4,096 字节/层。

PP1、同步调度、KDA align 模式、MTP1 且没有额外保留 token 时：

```text
完整注意力 ID = ceil(context / 640)
状态 ID = ceil(min(context, 4 + chunk_budget) / 4) + 1
KDA ID = 3 × (2 + 1) = 9
准入字节 = 三类 ID 总数 × 8,355,840
```

这是一个最大长度请求的启动下限，不是完整执行预算。跨块额外 ID 必须保留；
异步调度会增加在途 token，不能沿用同步预算。空块、前缀保留和额外并发还需要
预留。配置四个请求不代表四个最大上下文请求能同时驻留。

| 上下文 token | 当前 640 块，GiB | 当前 1,280 块，GiB | 32-token 状态页方案、1,280 块，GiB |
| ---: | ---: | ---: | ---: |
| 65,536 | 2.132 | 3.377 | 1.198 |
| 131,072 | 2.926 | 4.171 | 1.992 |
| 208,640 | 3.868 | 5.113 | 2.934 |
| 311,040 | 5.113 | 6.358 | 4.179 |

最近失败日志的 4.17 GiB 要求与精确结果 4.171142578125 GiB 一致。
可用值 3.72 GiB 只有两位小数，其舍入区间对应约 93,440–94,080 token
的准入上限，与日志的 93,440 一致。即使采用区间上界，131,072 上下文仍缺
超过 0.446 GiB 的缓存容量。

把上下文从 311,040 降到 208,640，可以抵消 640→1,280 的额外缓存 ID，
但不能为更大的执行缓冲提供额外余量。此前 65,536 上下文试验也出现过请求成功后
再次申请工作区失败。工作器若按分析余量的固定比例分配缓存，降低上下文并不保证
实际缓存分配随之减少。

## 状态页布局方案

32-token 方案把状态页设为 `[32,256]` FP32，页跨度为 10,240 个 FP32 元素。
每四个 token 的池从 `floor(offset / 4) * 4` 读取；MTP1 窗口为 33。
注意力逻辑页保持 640，压缩仍按四个 token 进行。

必须同时修改普通和驻留压缩写入器。目前它们要求 `[4,256]`，且把 `slot / 4`
当作页面地址，不能直接用于新布局。需先收集旧状态再写当前尾部，保留负 slot
掩码、请求隔离、前缀命中语义和推测拒绝边界两侧的池。目标/草稿图的元数据
需要使用新块大小并保持捕获地址稳定。

新准入状态页数为 `ceil(min(context,32+chunk_budget)/32)+1`，1,280 块只需
42 个 ID，而不是 322 个。原有全局分配器及两类填充页大小可保持。
比较 1,280/311,040 新布局与 640/311,040 旧布局，最低缓存加已知 MoE
共享缓冲预计减少 **0.858 GiB/卡**；这不是总内存节省的实测结果。

更复杂的备选方案是保留全部 322 个状态 ID，但单独配置压缩器物理存储，
理论可减少 2.358398 GiB/卡。该方案需要独立池或全局到本地 ID 的地址转换。
仅缩小张量描述符会使原内核访问越界。32-token 页方案需要更少的架构改动。

## 执行内存及限制

九个 A4 MoE 共享存储的计算精确复现历史值：640 块为 **93.016 MiB**，
1,280 块为 **170.633 MiB**，2,560 块为 **325.867 MiB**。640→1,280
增加 77.617 MiB，不能再按层数相乘。返回的 FP32 输出、路由临时张量、KDA/QSA
缓冲以及原生算子工作区均为额外项。

历史各卡总容量为 45.67/46.15 GiB；限制卡启动时空闲 44.61 GiB。
权重加载占 34.6368 GiB，虽然源码日志标签写 `GB`，实际除以 `2**30`。
必须按最受限的卡预算。

640 快照中 rank 1 已分配约 40.657 GiB、已保留约 41.938 GiB，全卡最小
报告空闲量为 1.924 GiB。rank 1 生命周期峰值已分配/已保留为
43.031/43.664 GiB，可包含门控测试和图捕获，不能当作单独的冷预填充峰值。
已保留量包含已分配量，不能把二者相加。

早期解码图日志记录 0.56 GiB，后续重新捕获记录 2.95 GiB 的分配增量，
它们不是独立的图池上界。启动时 non-Torch 占用也不是算子工作区峰值上界。
旧布局 1,280/131,072 的历史权重、最低缓存、已知 MoE 缓冲之和已达
38.975 GiB。在 45.67 GiB × 0.92 的预算下，其他全部图、持久张量、
临时峰值、外部工作区和碎片余量只剩约 3.042 GiB。这仍不是可行性证明。

## 验证与交付

[CPU 预算工具](../../../tools/glm_perf/prefill_memory_budget.py) 分开报告缓存准入和
完整执行可行性。每卡必须提供互不重复计算的持久张量、图池、临时峰值、外部
工作区、碎片和安全余量上界，并绑定确切候选及配置。任何未知或过期上界均阻止
可行判定；任一卡不满足即整体不满足。工具不生成启动命令。

新增 **45 个 CPU 测试全部通过**，覆盖真实分配器/缓冲形状的 AST 对照、历史
失败算术、跨页余量、并行批次、页地址、MTP1 边界位置、无效参数及未知/过期
预算拒绝。另有 24 组 CPU 情况与固定版本上游滑窗函数一致。Ruff 检查及格式通过。

页地址测试只确认池隔离及所需保留位置，不证明调度器回滚、压缩数值或图执行正确。
本轮无新硬件验证或速度提升宣称。

明细和未知物理上界。[启动回执](latest-launch-receipt.txt) 对应失败试验。
完整源码依据与 CPU 命令见英文报告。
