# M3.1 reasoning-loop isolation

The reported loop persists with the full 19-turn history and an empty KV cache.
A warm replay produces identical reasoning, content and tool arguments. The
loop is generated by the model, rather than fabricated by the tool parser. Removing expert INT8 compute did not eliminate it.
The investigation has not yet established why the source model would behave
differently on this conversation; no native source-FP4 agent baseline is available.

## Controlled continuations

The early-history cases reconstruct the first three completed tool turns from
the original Kilo session, using the old agent prompt and current repository
instructions. They are not exact original wire captures. All proposed tool
commands were recorded, not executed. The supplied tool results were fixed.
Greedy sampling and operator determinism were held constant.

| Case | Result | Scope |
| --- | --- | --- |
| Early history, reasoning retained | 192 tokens, two discovery calls | Further discovery at this point is not itself proof of a loop |
| Same history, reasoning omitted | 246 tokens, two discovery calls | Removing early thoughts does not force an answer |
| Same history, `tool_choice=none` | Same reasoning and raw tool-call XML, 192 tokens | This server retains tool schemas and disables parsing; this is not constrained no-tool generation |
| Late looping history, eager expert INT8 | 193 tokens, same repeated thoughts and commands | Reproduces the established continuation |
| Same late history, eager expert FP16 | 177 tokens, repeats intent to summarize, then more discovery | Expert INT8 arithmetic is not necessary for this continuation |
| Early history, eager expert FP16 | 273 tokens, two discovery calls | Same tendency; not a complete fresh agent trajectory |

Expert-FP16 tests retained selected dense INT8 projections and the same custom
W4 expert values. They are not source-FP4 tests. The bank layout conversion was
reversible, covered 342 banks, and retained all six worker processes. The saved
serving generation was restored afterward. No checkpoint shards were reloaded.

The source, converted and installed chat templates have the same SHA-256
(`provenance.json`). No message-boundary, reasoning, tool namespace or closing
response markers occurred inside the original 38 tool results. The original
session did not hit its output limit on completed tool turns. Earlier cache
checks are documented in
[the cache investigation](../minimax-m31-cache-investigation-20261025/README.md).

A final combined control removed both expert and selected dense INT8, disabled
partial graphs and used an eight-query attention tile to stay within the 160K
cache allocation's memory budget. The 5,549-token late-history replay still
returned the same repeated reasoning and two discovery calls (193 tokens).
All 342 expert banks and 348 dense projections were subsequently returned to
the serving INT8 configuration without restarting workers. Thus neither added
INT8 arithmetic nor partial graphs are necessary for this short continuation.
The custom stored W4 conversion remains in every hardware comparison.

## Full history and actual Kilo wire audit

A local-only mock captured Kilo's request from a fork of the original session,
using its old agent settings. It contains all 19 completed assistant turns,
reasoning and all 38 tool results in the same order as their calls. The original
session was not modified. The appended diagnostic `Continue` message was removed
for comparison; the interrupted twentieth thought was already absent from Kilo's
wire history. Tool-result contents and reasoning match our reconstruction.

A full reconstructed-history request used **29,577 prompt tokens**. It repeated
“I have a good picture. Let me summarize the project,” followed by upstream/git
and repository discovery calls. It returned 221 tokens with `tool_calls`:

- Cold: zero cache hits, physical caches cleared, 312.91 seconds.
- Warm: 29,568 cached tokens reused, 73.69 seconds.
- Reasoning, text, tool names/arguments and output token counts matched exactly.
  Generated tool IDs differ normally. Raw token-ID equality was not measured.

This is substantially stronger evidence against stale-cache reuse causing the
observed continuation than the earlier 5,549-token replay, which retained only
three late turns and omitted much previously gathered evidence. It does not
rule out every possible long-running cache defect or explain the original onset.

The `/tokenize` endpoint exposed a separate diagnostic pitfall: the pinned chat
protocol normalizes deprecated `reasoning_content` to `reasoning`, but its
tokenization protocol does not. The unnormalized request counted 28,280 tokens
and omitted historical thoughts. Canonicalizing the field gives 29,577, matching
actual chat usage. The new `tool_probe.tokenize_chat` helper normalizes a copy,
preserves tools/template options, and avoids silently changing the reference
conversation. Serving chat already handles the alias correctly; this is not the
cause of the loop. The actual final prefill batches were 393 cold and 9 warm,
not 120 as the initial unnormalized tokenization estimate suggested.

## Attempts to exit the pattern

Removing reasoning from the three late turns removed the repeated wording, but
still produced two discovery calls. Low reasoning effort produced one further
README/git call. A fresh conversation containing the README and repository facts
also chose discovery; one such turn is not itself a loop.

Appending an explicit user instruction to use existing evidence, avoid further
tools and answer in at most 150 words produced 288 output tokens, no reasoning,
no tools and a normal `stop`. The preceding unconstrained-length version also
started a project summary but hit the diagnostic 512-token cap. This shows that
new instructions are effective inside the previously looping conversation; it
is a behavioral escape, not a demonstrated correction of model fidelity. Output
factual accuracy was not separately scored.

## Numerical isolation

These comparisons use actual layer-3 activations from one decode token of the
previous synthetic 1025-token cache probe, not from the looping conversation.
All four selected experts were on rank 0. This small sample is diagnostic,
not a model-quality score or a representative accuracy evaluation.

For expert 52, compact and ordinary fused one-row dispatch matched exactly.
Fused decode versus eight repeated prefill rows had normalized RMS differences
of 0.246% for gate, 0.111% for up, and zero for down. This demonstrates a
shape-dependent numerical discrepancy in the expert path. It does not establish
that this discrepancy causes the loop or explain all prefill/decode differences.

On the same input, INT8 versus FP16 projection errors were 1.26–2.82%.
The broader CPU comparison of all four selected experts found 1.24–2.92%
projection error for native INT8 versus decoded W4. This is larger than the
maximum 1.28% observed in the original seeded-random promotion checks.

The custom W4 conversion introduced still larger differences from decoded source
NVFP4 weights: 4.95–11.50% for individual projections on common inputs, and
14.77%, 16.57%, 20.26% and 18.95% for the four complete expert outputs. The complete
expert comparison recomputes gate, up, activation and down independently for
source and W4, holding the input fixed. Both use FP16 weights/activations and
FP32 matrix accumulation; source activation quantization is excluded.

These measurements isolate loss introduced by the stored weight conversion,
separately from additional INT8 compute error. They make source-weight fidelity
a substantial unresolved concern, but **do not prove the cause of the agent
loop**. Source NVFP4 uses nonlinear E2M1 values with a scale for each row's group
of 16 values. The current signed W4 export uses one scale per 32-by-32 block;
this is a lossy requantization, not a byte-layout conversion.

## Evidence and limits

The follow-up [public report review](external-reports.md) found similar
overthinking and repeated tool inspection on hosted MiniMax services, an
effort-dependent repetition experiment, and a separate low-bit conversion
warning. These reports weaken attribution to our W4 conversion alone without
clearing its measured fidelity loss or establishing a common root cause.

Compact response summaries omit private request bodies and original tool outputs.
The original SQLite session remains local. Prototype scripts document the exact
fixed paths used in this investigation and are not production entry points.
Private session IDs are replaced with placeholders.
Large tensor traces and conversion receipts remain on the serving host.

A matched source-preserving agent comparison remains necessary to attribute
this behavior to quantization. Continuing a history already containing repeated
thoughts and discovery commands can reinforce the pattern even in an otherwise
working model. Neither successful short prompts nor local numerical tolerances
are sufficient to qualify the converted model's agentic behavior.

## Delivery validation

The service is restored and available with 163840-token capacity, selected dense
INT8, expert INT8 v15, activation v2, deterministic operators and all 240 partial
graph captures. All six worker PIDs are unchanged. A final counting request
returned the complete sequence and `stop`; pause and maintenance are both false.
This checks restoration, not broad coherence. No full-160K test was run.

The CPU suite passed **269 tests**, with 24 skips. The tokenization helper was
also checked against the running service and exactly matched the 29,577-token
chat usage. Required whole-repository formatting encountered preexisting
unrelated failures; its 225 unrelated automatic edits were reverted. Changed-file
hooks are checked separately. See the validation receipts in this directory.
