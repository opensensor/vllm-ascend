================================================================

Scope
-----
The previous resident-live-v16 used TP4/EP4, four request slots and a
262,144-token per-request limit, with roughly 1M tokens of aggregate cache.
It was not a validated single 1M-token context. The selected TP6 profile keeps
262,144 tokens per request and increases concurrency to six. It does not add
YaRN or claim accuracy at a single 1M-token context.

Restore on this host
--------------------
Use a fresh run directory for every launch; never reuse collective owners.
The qualified runtime contains both the committed Python tree and coherent
operator binaries. An archive of the Python repository alone replaces the
packaged OPP symlink with an empty directory: preserve the actual package.
The launch scripts validate required package directories and use the prior
qualified TP6 native extension. No transformers or CANN upgrade is needed.

From the profile root:
  python3 launch.py NEW_VERSION
  # Wait for /health and /v1/models, then:
  bash run.sh restore.py resident-NEW_VERSION

restore.py qualifies exact HC against loaded weights, installs it through the
resident transaction, attaches PLE without replacing existing graph/patch
owners, runs a real shared-prefix six-request verification, then disables
shadow comparisons. It stops on failure and preserves ownership for inspection.
Do not run it twice against the same session.

The PLE table owner must already be alive. After a host restart, create a fresh
owner with tools.qwen4exp.serve_ple_table using the base 300i checkpoint and
ple-table-source.json, then run prepare-ple.py. It verifies that the TP6 overlay
resolves to identical PLE checkpoint files before binding table metadata to the
overlay. Old /proc/PID/fd paths are invalid after the owner exits. Keep the owner
alive across server restarts; do not allocate six separate copies of the table.

Build the native host library using PLE_HOST_GATHER.txt, then run
ple-transport-gate.py --rank N separately for each N in 0..5. The selector build
must include max_requests=6 and the current native source; build it with the
CANN installation root, not its x86_64-linux subdirectory. launch.py checks
all six transport receipts against the exact host-library digest.

Validation and rejected candidates
----------------------------------
* Custom collective: changed inputs, FP16/FP32, all 16 geometries, multiple
  capture counts, eager interleave, opposite replay order, graph retirement,
  and clean six-worker process exits passed the full private gate. An earlier
  small probe passed math but failed process teardown; it was rejected and
  followed by a clean repeated gate and full gate.
* QSA CPU-reference gate passed TP6 widths/heads and rows 3,18,65.
* Selector: real checkpoint hash parameters, one through six request groups,
  18-token decode, 2048-token prefill hashing, empty groups, EOS, malformed
  boundaries and invalid tokens passed. Hashing alone does not validate DMA.
* Transport: all six devices passed exact real-table row/payload comparisons
  at 1,3,6,9,12,15,18 tokens, four/six groups and three input revisions; all 14
  private owners per device closed successfully. CPU tests cover rejection
  beyond 18 tokens and invalid packet receipts.
* Joined HC projection failed exactness at 12 tokens (max abs difference
  .00390625). Excluded. The replacement preserves original projection math;
  real HC weights at 3,6,12,18,256 rows and native edge cases passed exactly.
* The first PLE attachment used an old host library bounded to four devices
  and 12 tokens. It failed before method replacement. All collective ranks
  were explicitly retired before terminating that paused session. Worker
  admission errors now return receipts instead of leaving unread RPC replies
  that interfere with shutdown. The fresh session uses the qualified library.
* Shared-prefix retrieval passed cold at 5704 tokens, then all six concurrent
  branches returned the correct passphrase and reused 5632 prefix tokens.
  Six additional 256-token completions exercised the full 18-token decode
  shape under live PLE shadow comparisons on all ranks.
* Baseline HTTP smoke passed arithmetic, counting, indexing, capital and tool
  calling. One word-reversal question was wrong (DNESCA instead of DNECSA).
  This is not a comprehensive accuracy evaluation.

Measurements
------------
Baseline before pacing and resident HC/PLE restoration, fixed prompt budgets:
C1 median streaming decode: 30.89 tokens/s (three 256-token completions).
C6 aggregate end-to-end: 73.98 tokens/s (six 128-token completions).
Restored paced profile with the same prompt/output budgets:
C1 median streaming decode: 33.96 tokens/s.
C6 aggregate end-to-end: 69.26 tokens/s.
A longer six-by-512-token trial reached 79.86 aggregate end-to-end tokens/s;
its repeated C1 median was 32.69 tokens/s. Budgets differ: do not compare
79.86 directly with the 128-token baseline.
The earlier baseline preceded pacing: this is a complete-profile comparison,
not an isolated HC/PLE A/B. Pacing protects existing decoders but delays new
admissions, reducing the short C6 end-to-end rate in this sample.

An uncached 8192-token prompt arriving during a 512-token generation reduced
that generation from 32.33 to 19.99 tokens/s; the maximum post-arrival chunk
gap was 0.59 seconds. The long request TTFT was 37.50 seconds. This validates
one overlapping long prefill, not six simultaneous full-context prefills.

C6 includes prefill time. Do not compare it directly to historical C4 rates,
and do not attribute prefill fusion changes to decode speed.
