# The type-9 route works, and it is still signed

**Date:** 2026-10-28
**Status:** hardware-validated on the 310P at `matteius@192.168.53.187`.

This is the follow-up to `HDC-FILE-CHANNEL-20261028.md`. The HDC file channel
turned out to be able to reach the device's `aicpu/` staging directory, which
is the *type-9* package route — the one that had looked signature-free. It
does work, and the packages do install. But it turns out the type-9 package
is signed as well.

---

## 1. The delivery recipe

Three things had to line up, and two of them were mistakes of mine that
invalidated earlier results.

### 1.1 The whitelist must be *loaded*, not just edited

`drvHdcLoadFileTransWhiteList(path)` takes the path as an argument. If it is
not called, the driver's built-in default list is used and **every** send is
refused with `DRV_ERROR_DST_PATH_ILLEGAL` (52).

I edited `/etc/hdcFileTransWhiteList.cfg` and assumed the driver would
re-read it. It does not — it reads the file once, at load time, from the path
it is given. Every result before I started passing the path explicitly was
meaningless. This is the single most important thing to know about this API.

### 1.2 The API needs a client and a session

```c
drvHdcClientCreate(&client, maxSession, serviceType, flag);   // must succeed
drvHdcGetPeerDevId(node, devid, &peer);
drvHdcSessionConnect(node, peer, client, &session);            // must succeed
drvHdcSendFile(node, peer, file, dst_path, notifier);
```

Calling `drvHdcSendFile` on its own returns `DRV_ERROR_INVALID_VALUE` (3)
even for a destination that works.

### 1.3 V1 and V2 have different trusted base paths

| API | base path |
|---|---|
| `drvHdcSendFile` / `drvHdcGetTrustedBasePath` | `/home/HwHiAiUser/hdcd/device0` |
| `drvHdcSendFileV2` / `drvHdcGetTrustedBasePathV2` | `/home/HwHiAiUser/hdcd/device0/aicpu` |

`drvHdcSendFileEx` is **not exported** by this driver version, and the 6th
argument it takes is the peer dev id (the driver logs
`drvHdcGetPeerDevId Input parameter peerDevId is NULL` when it is zero).

### 1.4 What works

| Destination | API | Result |
|---|---|---|
| `.../hdcd/device0` | V1 | rc=0, delivered |
| `.../hdcd/device0/aicpu` | **V2** | rc=0, delivered |
| `.../hdcd/device0/aicpu` | V1 | rc=25, not delivered |
| any path outside the base | V1/V2 | rc=52, refused |

The `dst_path` must be a **directory**; a bare file name is refused with 52.
With V2 the destination is the `aicpu/` directory and the file keeps its own
name.

The whitelist entry needed is the device's own naming form:

```text
_Ascend310P-aicpu_syskernels.tar.gz * 0 104857600 64 0
```

(`name_full_check_flag=0` tolerates the `<hostpid>_` prefix the device uses,
and `save_sub_path=*` means the base path.)

## 3. But the type-9 package is signed too

The `ascend_aicpu` container is:

```text
  0x0000  outer header, 0x2000 bytes
  0x2000  "ascend_aicpu" header, 0x100 bytes
          +0x18  32-byte digest  = sha256(the gzip member)
          +0x58  256             header size
          +0x5c  64415294        gzip member length
          +0x68  9               package type
          +0x78  0x3a3aaa33      the "3\xaa::" magic
          +0x88  0x564d           the "MD" marker
  0x2100  gzip member
  ...     18 zero bytes + "cms\0" + 8 zero + u32 LE length (9201)
          + 9201 bytes of DER PKCS#7 (1.2.840.113549.1.7.2 signedData)
          containing a messageDigest attribute
            ccec98cbfad8b15125f560e7a3e3e36f30bbce22422fe56e77b25e1ca9441a43
```

The signature is over the package content, so it cannot survive a change to
the payload.

### 3.1 The isolation experiment

Four variants, each sent and then checked in the device log:

| Variant | Result |
|---|---|
| stock tar, CMS tail **stripped** | "by cms start" then nothing — **fails** |
| stock tar, CMS tail **kept** (control) | "Package verify success" → "Load package success, type=9" — **passes** |
| our modified tar, no CMS tail | "by cms start" then nothing — **fails** |
| our modified tar, CMS tail copied from stock | "by cms start" then nothing — **fails** |

So:

- the **CMS tail is required** — contrary to my reading of the disassembly,
  where `GetCmsInfoOffSetFromPkg` returning `0x2f` appeared to lead to a
  success branch (`mov w20, #0x0` at `+0x18f624`). In practice a package
  without a tail does not reach "by cms end". The `0x2f` path is not the
  success path it looked like.
- copying the stock tail onto a modified tar does not help, because the
  PKCS#7 signature covers the content.

### 3.2 What this leaves

Every route into the device's AICPU kernel tree is behind a vendor
signature:

| Route | Container | Signature | Verified by |
|---|---|---|---|
| type 0, `aicpu_syskernels` | esbc | RSA-PSS, 512 bytes, Huawei CSI CA | kernel `soc_verify` → `rsa_verify_soc` |
| type 9, `aicpu/` | `ascend_aicpu` | PKCS#7, 9201 bytes, in a `cms\0` block | tsdaemon `VerifyAicpuPkgByCms` |

The HDC file channel is a genuine and *unsigned* way to place a file on the
device — but the files the device will act on are all signed.

## 4. The one asymmetry that remains

The type-9 route differs from type 0 in *where the check happens*:

- type 0 is verified by the **kernel**, in `drv_pkicms.ko` /
  `drv_upgrade.ko`, against the esbc container's RSA-PSS signature, with the
  public key `"+Huawei CSI RSA-PSS Code-Signing Authority 20"` compiled into
  `hsm_firmware_update.ko`;
- type 9 is verified by **tsdaemon's user-space** CMS code
  (`CmsCbbVerifyPkg`, `cmscbb_verify_pkg.cpp`), against the PKCS#7 block in
  the `ascend_aicpu` container.

Two consequences worth exploiting:

1. **The type-9 check is name-driven at the tsdaemon level.** The tsdaemon
   CMS gate (`VerifyPkgByCmsEnhance` → `IsVerifyFlagValid` → `verifyFlag <= 7`)
   is the *same* gate for both types; it is the kernel's esbc check that
   type 0 additionally passes through. The device's default `verifyFlag` is 1
   (`SIGN_FLAG_ONLY_VENDOR`), so verification runs by default, and the
   policy file lives on the device's own filesystem at
   `/var/asdrv/dev<N>/device-sw-plugin/verify/flag` — which the 310P build
   has no writer for.

2. **The `verifyFlag` bypass is one value away.** `IsVerifyFlagValid` is
   `verifyFlag <= 7`; a value of 8 or more makes it invalid, and
   `VerifyPkgByCmsEnhance` then skips verification entirely and logs
   `"verify pkg[%s] no cms just rewrite"`. The only ways to get such a value
   onto the device are the writer the 310P build lacks, or code already
   running on the device.

## 5. The remaining, now well-defined problem

Everything needed for a working delivery path is in place:

- the file channel reaches `aicpu/` (V2) and the device acts on what arrives
  there (type-9 worker, confirmed installing);
- the type-9 worker does **not** go through the kernel's esbc/RSA-PSS check,
  only through the user-space CMS check;
- the user-space check is a *policy* check with a numeric bypass, and its
  policy file is on the device's filesystem.

So the question is no longer "how do we deliver a package" but **"how do we
get a `verifyFlag` of 8 or more onto the device"**, or equivalently "how do
we reach a device-side code path that lets us set the `usershadow` item
directly".

Two candidate directions, both now concrete:

- **The `usershadow` route**, from `USERSSHADOW-ROUTE-20261028.md`: the
  device's `drv_user_cfg.ko` whitelist (`whitelist_process_handler`) allows
  the `aicpu_scheduler` process — which is the uid-1000 process that loads
  our library — to call `halSetUserConfig("usershadow", ...)`. That needs
  our library to be loaded, which needs the `SandBoxSo=` channel, which is
  inside the signed payload. Circular unless the type-9 CMS check can be
  bypassed.
- **The `verifyFlag` route**: if the `aicpu/` route can be made to skip the
  CMS check, then a package with *no* `cms` tail and a modified
  `version.info` would be installed, and its `SandBoxSo=` library would be
  renamed into `sand_box/` — completing the loop.

The decisive question is therefore narrow and answerable: **what exactly does
the device do when `GetCmsInfoOffSetFromPkg` returns 0x2f?** The
disassembly says "return success", the experiment says "no". Reconciling
those two is the next step, and it is a matter of reading
`CmsCbbVerifyPkg::VerifyAicpuPkgByCms` and `GetCmsInfoOffSetFromPkg` in
full rather than the excerpts.

## 6. Tooling

On the card host, `/var/local/ascend-work/tools/`:

| Tool | Purpose |
|---|---|
| `hdc_plant2.c` | HDC send: client+session flow, whitelist loading, V1/V2 selection, dst as a directory |
| `build_type9_mod.py` | builds a type-9 package (adds a `.so` to `sand_box/`, rewrites `version.info`), and can copy or strip the CMS tail |
| `isolate.sh` | the four-variant CMS isolation experiment |
| `wl_test*.sh`, `v2_test.sh`, `plant_test*.sh` | the destination and whitelist probes |
| `drvlog_test*.sh` | probes that correlate each result with the host driver's own syslog lines |

`/var/log/syslog` carries the host driver's HDC messages with file, line and
function name, and is the fastest way to see *why* a send was refused —
`drvHdcSendFileParaCheck`, `drvHdcGetTrustedBasePath`, `recv_reply`.

`msnpureport -g debug -d 0` raises the *device* log level; the host driver
log level is separate. The device's tsdaemon trace is in
`slog/dev-os-0/run/device-os/device-os_*.log` and is the record of what the
device actually did with a file.
