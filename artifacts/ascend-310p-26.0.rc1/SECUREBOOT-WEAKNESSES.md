# Ascend 310P secure-boot weaknesses — ranked list for rootfs replacement (T14 synthesis)

**Date**: 2026-09-12 · **Method**: consolidation only — no new RE. All evidence levels are inherited verbatim-or-below from the source files in `evidence/secureboot-hunt-20260911/` (tasks T1–T13, T16); nothing is upgraded.
**Ranking criterion**: consequence for a *maintained rootfs replacement* that must both **BOOT** (pass whichever boot stage owns its authentication) and **OPERATE** (survive the runtime gates). Boot-deciding items rank ahead of OPERATE-only items. An entry may carry two or three levels when its parts differ — each part is then labeled separately.

## Ranked weaknesses

### 1. Boot-verdict ownership forks on the BL31 variant — and which variant boots is unknown
**What/where**: `device-aarch64/boot-components/hboot2-fip-{132100,172100}/bl31.bin`. BL31-132100 embeds an entire CMS/X.509 verify engine that BL31-172100 lacks: AOID DER/OID table 0x20a1b–0x20dd0, BOTH named roots (`Huawei Root CA` @0x1fbe9, `Huawei Integrity Root CA - G2` @0x201ad — same names as the runtime module's roots), pbroot/CRL/cms-engine error family 0x2377a–0x23a48 (Begin/Update/Final shape), secure-header gate 0x2144e–0x214c6, nvcnt-vs-eFuse compare+write 0x216f9–0x21ad6, usr-cert path, ini hash-list gate (`cur image hash not in list!` 0x21430). BL31-172100 keeps only TEE-verify (0x1701e), TSPD, and UFS-nvcnt cleanup — container-verify machinery ABSENT. Which FIP (0x132100 vs 0x172100) the card boots, and why BL31 differs between the copies (BL2/BL33 bit-identical), is not selected by anything observed (`bl31-hsm-split.md` §1/§4; `bl31-recon.md` §4).
**Level**: **Observed** (the string-presence/absence delta between the two carves) / **Interpreted** (kernel/dt/rootfs boot verdicts = BL31 on the 132100 build — pipeline membership by image_type, no image-name literals) / **Unknown** (the FIP selector; the 172100 verdict-owner — HSM-side or absent at that stage).
**For our case**: the master fork of the entire boot question. If 172100 boots, a replaced rootfs may face no boot-stage CMS verdict at all (major opportunity); if 132100 boots, BL31 owns the verdict under a policy we cannot see yet (T9 U-G: which root per image_type, fallback behavior — card-time either way). Obstacle-or-opportunity, undecided by one single observation.
**Card-time**: which FIP slot boots; annotated BL31 boot log — do `usr cert cms vef`, `hw_cms_image_verify_simple stop!`, `cur image hash not in list!`, `no need nvcnt check!` fire, and for which image_types.

### 2. Dual-root + PSS→PKCS#1v1.5 fallback: cross-root acceptance for every ID except 15-with-eFuse (the marquee selection-policy finding)
**What/where**: `drv_pkicms.ko` — `pkicms_verify_cms` 0x9968 seeds `g_pkicms_sign_alg` (`.bss+0x20`, NOBITS) with the PSS word `0x08010000` @0x99bc and on failure falls back with word `0` @0x9aec; the root is picked by alg-type bits [21:16] via 0x67ec→0x5d90→`pkicms_get_cert_data` 0x5bb8 (type 0 → PKCS1 root `.rodata+0x790`; type 1 → G2 root `.data+0x0`). The eFuse flag (`pkicms_get_sec_check_enable_flag` 0x3534 → reg 0x8126E080 via `pkicms_read_efuse_reg` 0x3440) never picks a root: `flag==1 ∧ ID==15` (HAL ABL_PATCH) is its only effect — forbidding the fallback (gate 0x99e8–0x99f0; eFuse-read failure ⇒ −5, no verify at all). BSS-zero default = legacy root (`.init.text` seeds nothing); the inner verifier overwrites the word mid-verify from the payload's own alg field +0x50 (0x8d6c–0x8d70); the custom path 0x943c can instead trust file-read **customer certs** (cert-type 0..7) (`root-cert-selection.md` §2–5; `pkicms-inventory.md`).
**Level**: **Observed** (engine structure, seeds, gate, both extracted roots, BSS default) / **Interpreted** (only the "policy intends the other root" framing of the cross-root acceptance; custom-mode customer-signing relevance) / **Unknown** (whether any boot stage applies this same table — T9 gotcha #4: BL31 has its own engine + both roots, the module table must NOT be assumed for boot; alg WORD bits [15:0], U1).
**For our case**: **Opportunity.** A payload signed under either Huawei root transparently validates at runtime/update on fallback for every ID except ID-15-with-eFuse=1 — a policy soft spot we can ride; and the custom-cert file branch is the sanctioned door for customer-signed payloads (same two-attempt engine applies to them too).
**Card-time**: read reg 0x8126E080 (F value) + security-lifecycle/customer-mode query; boot-log evidence on whether BL31 mirrors the fallback (U-G).

### 3. The outer signature does not bind container bytes — the device-side digest is a header-declared range matching no shipped-file slice
**What/where**: all four parsed `evidence/<image>.p7b` are PKCS#7 signedData with SPC contentInfo 1.3.6.1.4.1.311.2.1.4; the message-digest authAttr is **constant** `af70de12…` across all three 9201-B PSS structures (Image/dt.img/rootfs) → the PSS outer signature binds the CMS-internal blob, not the container; the per-image binding slot is the spcIndirectData content-hash (@DER 131/5614). None of 12/12 tested plain ranges matches any digest — whole-file, `[0,p7b)`, incl-sig, file-minus-12,753-tail, rootfs gzip-stream `[8448, +109,359,417)`, and file-minus-22,009 all fail. Device-side the inner verifier digests `file[blob+0x458, +len(blob+0x45c, fallback blob+0x4f0)]` via `pkicms_calc_digest` @0x8944 and 32-B-compares vs the header-stored digest @blob+0x2c (0x8964–0x8a6c) (`inner-verifier-findings.md`).
**Level**: **Observed** (SPC OID, constant msgDigest, content-hash positions, 12/12 non-matches) / **Interpreted** (the inner signs a loader-defined header-stripped range; Image's `image_size` header zero) / **Unknown** (the exact runtime range — card-time kprobe @0x8944 — and which of Image's two sigs, 3819-B PKCS1 vs 9201-B PSS, is enforced on any path, U-D; dt/rootfs carry only the PSS one).
**For our case**: the mechanical constraint on producing a re-signed repacked rootfs: "our file's SHA-256" is simply not what the container signature claims, so a re-pack must re-digest over exactly the loader-declared range and re-sign the p7b to match. Process obstacle until the kprobe pins the range, then routine.
**Card-time**: kprobe @0x8944 dumping the offset/len args + `[cms_blob+0x2c]`, and rehash those exact device-side ranges (plus the decompressed-cpio hash for rootfs).

### 4. Runtime gate stack: `module.sig_enforce=1` is the one hard non-rootfs-removable gate; SELinux locks down late; IMA/EVM/lockdown leave the field
**What/where**: the effective cmdline is recovered offline from `chosen/bootargs` of all 16 FDTs in `device-aarch64/images/dt.img`: all end with `module.sig_enforce=1`; none has `root=`/`lockdown=`/`integrity=`. `CONFIG_MODULE_SIG_FORCE` is off (config :985) — the bootarg flips rejection on, one-way until reboot, and bites at runtime too (vendor `.ko` are `insmod`-loaded from `/var`); 89/89 staged `.ko` carry the signature magic but the vendor key's trust anchor is Unknown (`SYSTEM_TRUSTED_KEYS=""`). SELinux permissive static (`etc/selinux/config:7`) with the final `echo 1 > /sys/fs/selinux/enforce` at `device_sys_init.sh:1091` (via rcS:24); IMA doubly dormant (zero callers of `ima-init`, no `integrity=` bootarg, no `/etc/ima/digest_lists`); lockdown `LOCK_DOWN_KERNEL_FORCE_NONE` (`runtime-gates.md` #1–#6, #8).
**Level**: per-part — bootarg/config/script presence **Observed**; the enforcement effect on replacement `.ko` **Interpreted**; the signing-key trust anchor, EVM effective state, and any UEFI-time cmdline append **Unknown**.
**For our case**: **Obstacle** component: any module we rebuild from source loses its appended signature and must satisfy `sig_enforce` with an Unknown trust anchor (controllable-by-rootfs = "no"); kept vendor `.ko` pass untouched. **Opportunity** everywhere else: no verity root, dormant IMA, no lockdown, SELinux permissive through most of boot, setuid/sudo surface fully rootfs-owned.
**Card-time**: `/proc/cmdline` vs the recovered bootargs (UEFI-append check); which key the kernel trusts for module sigs; EVM xattr state on replaced files.

### 5. Zero verification on the Linux boot path — every `soc_verify`/`pkicms` caller is runtime-load or update
**What/where**: caller matrix (`soc-verify-callers.md`): C1 `drv_upgrade.ko dev_upgrade_verify_image` 0x5b10 → `soc_verify(1)` @0x5be8 (fail: abort, ret 0x10e); C2 `dev_upgrade_verify_patch_task` 0x6e74 → `pkicms_verify_cms(15)` @0x7044 (fail: log-and-continue); C3/C4 `drv_platform.ko` TS-fw checks (id 2 @0xe718, id 0 @0xe820) through a dynamic `__symbol_get` resolver; the host ships the 8 boot images and issues **zero** verify calls (whole-file grep); two disjoint ID namespaces (SOC_VERIFY_IMG_ID vs HAL_IMG_ID; ID-15 = ABL_PATCH, absent from the loader table, never on the boot transport).
**Level**: **Observed** (call sites, enforcement branches, zero host-side calls) / **Interpreted** (the two-namespace split — "strongly anchored"; some matrix rows explicitly Unknown, U1–U8).
**For our case**: **Neutral — enabling.** Linux adds no boot-path check our replaced rootfs must pass, which is why the boot question concentrates entirely into ranks 1/9/10; conversely our runtime exposure sits at the update/load callers, where rank 2's fallback policy governs.
**Card-time**: none required for this entry alone (residual cpio.gz ID=3-vs-8 mapping, U6, settles with the rank-1 boot capture).

### 6. process-manager hash gate: a mutable, boot-cached policy file — but a wrong hash silently never forks the daemon
**What/where**: `usr/bin/mdc/base-plat/process-manager/process-manager` — check fn 0x41d20: basename map lookup (**miss ⇒ pass, no hashing**), else `popen("sha256sum "+path+"|cut …")` @0x41e6c (≤6 retries) then memcmp+length-eq vs the cfg value; start gate Y 0x2f4e8 immediately before the only two `fork@plt` sites — on fail, syslog `PROCMGR : IntegrityProtect … has been modified` and the fork is skipped. Config `/etc/mdc/base-plat/process-manager/bin_hash.cfg` (path hardcoded at rodata 0x6ae88, 15 `name=sha256` lines) parsed **once at procmgr boot** behind a once-guard atomic (wrapper 0x15fa8, once-byte @GOT 0x91f58; cfg loader 0x42210), zero script references anywhere; cfg absent ⇒ empty map ⇒ **entire gate fail-open** (island 0x42690) (`procmgr-hash.md`).
**Level**: **Observed** (call structure, once-cache, fail branches, hardcoded path) / **Interpreted** (start-reject retry loop under `on-forever`; missing-cfg fail-open extrapolation from the empty-map branch) / **Unknown** (procmgr-start vs DSI:1091 enforce ordering and post-enforce `popen`/`sha256sum` allowance; libtsd* secondary consumers of the same cfg).
**For our case**: **Opportunity with a maintenance duty.** The cfg is a rootfs file we control; replacing one of the 15 listed binaries REQUIRES editing `bin_hash.cfg` **before boot** (map cached), else the daemon never starts — obstacle-shaped if forgotten; unlisted binaries, renamed listed ones, or a removed cfg are free passes.
**Card-time**: procmgr start time vs DSI:1091; one hash-edit-then-reboot round-trip; `sha256sum`/`/bin/sh` resolvable under enforce.

### 7. Boot revocation is never CRL-based: the HSM checks an immutable eFuse RIM; CRL machinery is runtime/update with fail-open branches
**What/where**: `revocation.md` — HSM: revocation decision = cert subkey_id vs **efuse rim** (`subkey_revoke_check` string @0x1bd7c, host region 0x10d00–0x113b8 inferred; `rotpk is zero…efuse` family), zero root-key material from files, zero CMS/CRL/X509 strings in `hisserika.bin`; module: `pkicms_crl_pre_compare` 0x6118 has exactly one caller (`pkicms_hw_crl_compare` 0x72a0), DecodeCrl failure is log-only with return forced to 0 (`w19=0` @0x6394), a compare error writes status 3 yet returns rc 0, and neither CRL entry point has any external caller/importer in the 90-module rootfs; the installer's fail-opens (`device_crl_check.sh:155-161` extract-fail→return 0; `:427-430` lib64-absent skip; `:436` one-shot status file) run on the **host CPU**, not the card.
**Level**: **Observed** (module control flow, call-site census, installer lines and propagation) / **Interpreted** (HSM efuse-driven verdict — string-anchored; "user.crl cannot plausibly drive the HSM" ; lib64-skip reachability on first install) / **Unknown** (U1 who would ever call `pkicms_(hw_)crl_compare`; U3 whether BL31 forwards `/CMS/user.crl|user.xer` bytes into the HSM mailbox; U4 live rim/subkey values).
**For our case**: **Opportunity.** With an unchanged signing chain nothing host-controllable can trigger a boot-time revocation REJECTION, and revocation passes *silently* — "CRL OK" is indistinguishable from "CRL never asked" on the boot path. Residual controllable risks are upgrade-time only (stale `/root/ascend_check/Ascend310P.crl`; `/etc/pss.cfg` mode vs ret 6). Tension carried: the plan brief anchored `subkey_revoke_check` at 0x1c73b — that string is `root_pubkey_verify`; the corrected anchor is 0x1bd7c.
**Card-time**: `/proc/kallsyms` + `lsmod` diff with the full driver loaded (U1); user.crl presence-toggle boot A/B vs HSM mailbox log (U3).

### 8. Ten CMS-level `Cmscbb*` imports are defined by NO rootfs module; the HSM is a verify-decision service over supplied material, not a CMS stack — load base assumed
**What/where**: `drv_pkicms.ko` carries 10 `SHN_UNDEF` `Cmscbb*` imports (the 8 in `symbol-providers.json` **plus `CmscbbCrlCompare`/`CmscbbCrlFree`**); none of the 90 scanned rootfs modules defines any of them (`pkicms-inventory.md`). HSM `hisserika.bin` = ARM Thumb-LE (HIGH; `hsm-isa.md`), service dispatch = TABLE of 26 entries @rodata 0x163e8 + 3-entry secondary @0x16570, `service_soc_verify` host 0xd638 (the single Observed pool xref, dword 0x10a271ed @0xd6d8), local policy on efuse rotpk/rims/nv-cnt/head-magic/img-id over host-addressed data on PKE/HASH engines, and **zero CMS/PKCS#7 parser strings** ⇒ container parsing stays host-side (`hsm-verify-path.md`).
**Level**: **Observed** (import list, no-definer census, 26-entry table, zero-parser-strings negative) / **Interpreted** (HSM-channel hypothesis for the unresolved runtime imports; load base B=0x10a10000 from 261/611 exact-start pointer hits) / **Unknown** (which loader satisfies the 10 imports at module load; proof of B; mailbox cmd-id ↔ table-index correspondence; why five service-name strings are never referenced).
**For our case**: **Neutral for boot; Unknown-dependent for update/OPERATE.** Known tension carried openly, and it resolves cleanly: BL31-132100's own CMS engine (boot stage, rank 1) ≠ the runtime `Cmscbb*` provider — runtime provider and boot-stage engine may legitimately differ. But whether the `soc_verify`-class runtime/update checks we may come to depend on actually function hinges on this provider resolving on-card.
**Card-time**: `/proc/kallsyms | grep -i cmscbb` + `lsmod`; `hsm_firmware_update.ko` boot-copy hexdump/log (settles B, shared with T10); one mailbox/IPC capture correlating cmd-id with table index (T8 U3 rides along).

### 9. NVCNT anti-rollback: same-stamp accept is plausible, no boot-stage fuse-advance observed on the Linux side, BL31's burn policy unknown
**What/where**: `nvcnt-rollback.md` — counter authority lives behind the HSM channel (`soc_get_nvcnt` @`hsm_firmware_update.ko` 0xa38, `hsm_invoke_cmd` @0xad4, slot ≤3 guard); Linux consumers are advisory-only (`soc_verify_get_nvcnt_thread` @`drv_pkicms.ko` 0x4af0 — read+log, zero compare, always returns 0) or presence-gates (`pkicms_nvcnt_read` 0x3948, sole caller inner @0x8cf0, skipped for ID 15); fuse-write on the Linux side is update-path only (`sec_img_sync_and_efuse_update` @hsm_firmware_update.ko 0x998, cmd constant 0x7004, sole captured Linux caller `dev_upgrade_sync_proc`); BL31 carries BOTH compare and write strings (`nvcnt cmp fail … efuse_bit_pos`, `write nvcnt ret`, skip branch `no need nvcnt check!`). Installer `FEATURE_NVCNT_CHECK=n` disables only a host image-vs-image **consistency** check that never touches the device's burned value.
**Level**: **Observed** (host lifecycle, kthread non-compare, update-only advancer, BL31 capability strings, installer scope) / **Interpreted** (`≥ burned` monotonicity from `efuse_bit_pos` semantics; the same-version plausible-accept verdict) / **Unknown** (BL31 per-boot burn-vs-skip enforcement class for the rootfs image_type — answers partially via the rank-1 boot log, burn policy still Open; zero/absent-class dispatch; HSM instruction-level compare site — flat-Thumb floor region 0xefc8).
**For our case**: **Neutral-to-opportunity.** No observed enforcement stage requires a counter move for a same-version modified rootfs; re-sign with a stamp ≥ the burned value and only a LOWERED stamp can reject.
**Card-time**: eFuse counter readback + boot-log class (`no need nvcnt check!` vs `nvcnt cmp fail`) for the rootfs image_type.

### 10. Who verifies BL31 itself — the chain anchor is entirely upstream and not in hand
**What/where**: BL2 (bit-identical in both FIPs) shows **zero** verify/cert/cms/efuse/sign strings among its 33 total, and every FIP-TOC entry flag is 0 — no signing/encryption bit at TOC level (`bl31-recon.md` §3/§4). Current model (`bl31-hsm-split.md` §6): BL31 — and BL2, and the UEFI fd body — are authenticated, if at all, **by the stage that loaded them** (BootROM/HBOOT1, unacquired per T6), not by BL2 and not by any in-band TOC bit.
**Level**: **Observed** (the absences) / **Unknown** (the loader-stage behavior — halt-vs-continue on an altered image; BootROM packaging status; the BL33-entry-carries-`.gitignore`-text packaging anomaly and who authenticates the real UEFI body, U-E).
**For our case**: **Neutral** for a rootfs-only swap (we touch no boot component), but it caps model confidence globally: the root of trust has never been examined; it becomes an obstacle only if we later replace boot components ourselves.
**Card-time**: HBOOT1/BootROM string grep (T6 acquisition question re-renders as a card/portal question); boot-with-modified-BL31 test if ever needed.

## Boot trust model as currently reconstructed

The boot chain begins at an unseen anchor: an on-die BootROM (Interpreted — named in no package list) is assumed to start HBOOT1 (packaged, download-gated, not in hand), which loads the HBOOT2 UEFI fd carrying two FIPs at a fixed 0x40000 stride whose BL2 and BL33 entries are bit-identical but whose BL31 payloads are functionally different builds — a variant question the card answers on first boot log. BL2 itself verifies nothing (zero verify strings) and the FIP TOC carries no signing bit, so BL31's authenticity, if checked at all, is the loading stage's business — the unresolved dashed edge at the top of the chain. The boot container verdict for kernel/dt/rootfs then belongs to BL31 **if** the 132100 build runs (its own CMS/X.509 engine, both Huawei roots embedded, CRL/nvcnt/sec-header/ini-hash gates, with a customer-cert "usr cert" path); the 172100 build carries no container-verify machinery beyond TEE, leaving that verdict either HSM-side or absent. The HSM appears throughout as a crypto/decision **service** — efuse rotpk, subkey-rim, nv-counter, head-magic, img-id checks over host-supplied material on its PKE/HASH engines — never a CMS parser; and the runtime Linux stage adds **nothing** at boot: host soc_verify/pkicms activity is runtime/update only, with the runtime gates that actually bite a replaced rootfs being `module.sig_enforce=1` (from the recovered dt.img bootargs), the process-manager hash file, and late SELinux enforce — while verity, IMA, and lockdown are off by configuration. **Model confidence: MEDIUM** — the chain topology and every mid/late-stage absence are Observed-anchored; the two dashed edges (who verifies BL31; which FIP slot boots) sit exactly where the whole difficulty concentrates.

```
BootROM [on-die? Interpreted] -.-> HBOOT1_a/b [packaged, unacquired] -.-> HBOOT2 UEFI fd {FIPs @0x132100 | @0x172100}
  -> BL2 [zero verify strings; TOC flags=0] -> BL31 {132100 full CMS/X.509 engine | 172100 thin: TEE+TSPD only}  [selector? - - -]
  -> kernel Image + dt.img + rootfs (RAM initramfs; rw remount rcS:7)
[chain anchor — dashed] BootROM/HBOOT1 = sole unseen verifier; no in-band TOC signing bit
  BL31 -.-> HSM hisserika: decision service on supplied material (efuse rotpk/rims/nvcnt; NO CMS parser)
  Linux (runtime/update ONLY) -.-> Cmscbb provider unresolved [HSM channel? -> /proc/kallsyms]
```
